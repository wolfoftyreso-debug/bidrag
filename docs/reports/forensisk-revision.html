3Faktisk runtime-modell

  • Frontend: statisk SPA (Vite-bygge → apps/web/dist). Ingen SSR, inga klienthemligheter, inga VITE_-variabler — allt går mot /v1 på samma origin. Servas av Vercel (statiskt) eller av API:t via @fastify/static (container).
  • Backend: ett Fastify-API. Två startvägar: src/index.ts (långlivad process: migrerar vid start + startar pg-boss-worker) och api/index.ts (serverless: ingen migrering, ingen worker; instans delas mellan varma anrop).
  • Persistens: Postgres via pg-pool (DATABASE_URL, PG_POOL_MAX); Drizzle för alla queries; DIRECT_DATABASE_URL respekteras av migratorn.
  • Filer: dokumentvalvet kräver objektlagring — disk-driver (kräver beständigt filsystem) eller Supabase Storage-driver (kräver inget filsystem). Inga andra filberoenden i runtime.

4Databas-forensik

PostgreSQL, 34 tabeller i public: tenants/users/memberships/invites (flerhyresgäst), applicant_profiles/projects (fakta), authorities/funding_opportunities/rule_versions (kunskapsgraf med effective-datering), matches/funding_stacks, application_cases + budget_lines/canonical_answers/ submissions/submission_receipts/decisions/reporting_requirements/payment_milestones (ärenden), documents/case_documents (valv), sources/source_snapshots/review_queue (inhämtning), notifications/reminders/correspondence_events, audit_events (append-only), payments/receipts (köp + verifikationer med egen nummersekvens), refresh_tokens. FK:er med genomtänkt on-delete (tenant-kaskad; kvitton överlever radering), index på heta vägar, pengar i öre (integer), JSONB för fakta/regler/planer.

Migreringar: 6 st deterministiska SQL-filer (0000–0005) versionerade i Git, körda av Drizzles migrator i CI, test och deploysteg. 0005 slår på RLS (deny-all, inga policies) för alla tabeller och återkallar anon/authenticated-grants; ett invarianttest fäller CI om en framtida tabell saknar RLS. Seeddata: 51 stöd/29 myndigheter som idempotent seed-skript.

Supabase-kompatibilitet: hög — ren Postgres utan extensions utöver standard; RLS-migreringen är skriven för exakt Supabase-exponeringen; pooler-hänsyn (transaction mode) finns i migratorn. Ingen migrering utförd i denna revision.

5Autentisering & auktorisering

  • Register/login/logout/refresh/me finns; lösenord scrypt med per-användare-salt; refresh-tokens roteras och lagras hashade; cookies httpOnly + secure i produktion; origin-guard som CSRF-försvar; hårdare rate limit på auth-endpoints.
  • Lösenordsåterställning saknas och e-postverifiering saknas — konto skapas direkt. (Rapporterat, ej åtgärdat.)
  • Auktorisering i applikationslagret: varje query är tenant-scopad (tenant_id ur verifierat medlemskap, aldrig ur klientdata); främmande resurser ger 404, inte 403; roller (owner/administrator/applicant/contributor/reviewer/finance/data_curator) via requireRole; admin-/kuratorsytor kräver admin/data_curator.
  • Cross-tenant-åtkomst till sökningar, analyser, betalningar, kvitton, dokument: verifierat spärrad av dedikerade isolationstester (tenantIsolation, payments, gdpr) — inklusive försök att sätta främmande X-Tenant-Id.
  • RLS på databasnivå är deny-all-mur mot PostgREST-vägen; applikationens behörighetsmodell ligger i API:t (API:t ansluter som tabellägare).

8Betalnings-forensik

Implementerat i dag — kedjan är redan "betalning är den auktoritativa händelsen":

  • payments-tabellen motsvarar det föreslagna payment-recordet: id, tenant/projekt, kind (analysis_unlock), belopp i öre, valuta, provider, status pending / confirmed / failed / cancelled, provider_reference, receipt_email, created_at, confirmed_at.
  • Entitlement finns som härledning, inte som egen tabell: isProjectUnlocked() = "det existerar en bekräftad betalning för projektet". Ingen expires_at (engångsköp per analys). Frontend litar aldrig på klienttillstånd — teasern/402:an avgörs server-side per anrop, verifierat av läckagetester.
  • Bekräftelse → transaktion bokförd → kvitto utfärdat (i samma DB-transaktion, idempotent på payment_id — dubbla callbacks kan inte ge dubbla kvitton) → upplåsning observerbar. Kvitton: löpnummer ur sekvens, brutto/netto/moms fryst i öre, säljaruppgifter, omskickbart mail.
  • Tillstånden "initiated/pending/verified/failed/unlocked" särskiljs alltså: initiated+pending = pending-raden, verified = confirmed, failed = failed, unlocked = härlett ur confirmed.

Inte implementerat: QR-generering, Swish-anrop, callback-verifiering (webhooken svarar 503 på allt), separat entitlement-tabell, samt anonymt köp utan konto — i dag krävs registrering före betalning eftersom betalningen hänger på tenant/projekt. Mock-providern är avstängd i produktion per konstruktion (NODE_ENV-villkor i config). Ingen Stripe-kod existerar.

Öppet beslut som styr implementationen: Swish Företag (manuell avstämning, ingen callback), Swish Handel (m-commerce-API med QR + callback via mTLS-certifikat från bank) eller betalpartner (t.ex. PSP med Swish + webhook). Verifieringskoden ser olika ut i alla tre fallen; providergränssnittet i paymentProviders.ts är byggt för att bära vilket som helst av dem.

9E-post

Ja — via services/email.ts: Resend om RESEND_API_KEY finns, annars SMTP, annars auditloggat "skipped". Utskick i dag: kvitton (fullt verifikationsdokument, omskickbart), deadline-påminnelser/notiser (14/7/3 dagar, dedup), regeländringsnotiser, teaminbjudningar. Mallar är text i koden, separerade från UI. Ingen e-postverifiering vid registrering, ingen lösenordsåterställning (hänger ihop med §5-fyndet).

11Deploykompatibilitet

Vercel: kompatibel — konfigurationen finns redan (vercel.json, api/index.ts, cron-scheman, SPA-fallback) och serverless-entryn är röktestad genom hela köpresan. Villkor: STORAGE_DRIVER=supabase, poolad DB-anslutning, CRON_SECRET satt, migreringar som deploysteg. Kallstart bygger appen (~100-tals ms). Källhämtningsjobbet är sekventiellt och ryms i 60 s-budgeten vid nuvarande källvolym (~7); växer volymen behöver jobbet chunkas.

Supabase: kompatibel — Postgres: ren SQL, RLS deny-all förberedd; Storage: driver implementerad (dock ej integrationstestad mot riktigt projekt — kräver nycklar); Auth: används inte (egen auth, dokumenterat beslut); Edge Functions: används inte (inget krav identifierat); pooler: hanterad i migrator + pool-storlek.

15Säkerhets-forensik

NivåFynd
HIGHLösenordsåterställning och e-postverifiering saknas: fellstavad adress vid registrering = permanent utlåst konto, och kvitto-/notismail kan gå till fel adress. Blir viktigare i samma stund riktiga betalningar aktiveras.
MEDIUMRate limiting är per processinstans — på serverless ger det svagare globalt skydd mot brute force (auth-endpoints har egna hårdare gränser, men även de är per instans).
MEDIUMUtan ClamAV accepteras uppladdningar som scan_unavailable (synligt, men filer kan delas vidare i team). Magic-byte/typ/storlek kontrolleras alltid.
MEDIUMDELETE /v1/documents/:id raderar DB-raden men inte lagringsobjektet — kvarlämnade filer tills GDPR-radering/retention. Lagringsläcka, inte åtkomstläcka (nedladdning kräver DB-raden).
LOW/metrics är oautentiserad (containervägen; antar intern skrapning). På Vercel oåtkomlig via rewrites.
LOWResend-anropet saknar explicit timeout (Storage-drivern har 30 s). Mail är best-effort och blockerar aldrig upplåsning, så effekten är begränsad.
INFOPositivt verifierat: inga hemligheter i Git; inga klienthemligheter; parametriserade queries överallt (Drizzle) — ingen SQL-injektion funnen; React-escaping + ingen dangerouslySetInnerHTML; SSRF-guard på inhämtning; upload-allowlist med magic bytes; betalupplåsning kan inte påverkas av klienten (server-side-härledning, läckagetestad teaser); mock-betalning produktionsspärrad i config; webhooks avvisar allt tills signaturverifiering finns; RLS deny-all + CI-invariant; fältkryptering för externa identifierare; append-only audit; 404-inte-403 för främmande resurser.

17Teknisk skuld med deploypåverkan

  • Storage-drivern för Supabase är skriven men aldrig körd mot ett riktigt projekt (kräver nycklar) — verifieras första dagen.
  • Ingen lösenordsåterställning (se §15 HIGH) — bör finnas före betalande användare.
  • Per-instans rate limiting på serverless (global limitering är ett framtida beslut, inte en gateway).
  • Source-fetch är sekventiell — ok för ~7 källor, chunkas innan kunskapsbasen växer 10×.
  • pg-boss-schemat ligger kvar i databasen även på Vercel-vägen (oanvänt, ofarligt).
  • Momsklassningen (25 % default) är konfigurerad men inte bekräftad med redovisning — måste vara rätt från första riktiga kronan.

18Slutlig bedömning

Current state

Komplett, testad flerhyresgäst-plattform för rättighets-/stödutredning med betalvägg och kvittolager; monorepo med ren domänmotor, Fastify-API (34 tabeller, ~60 endpoints), React-SPA; dubbla deployvägar där Vercel + Supabase är förberedd och dokumenterad som primär.

What actually works

Hela produktvägen intag → analys → teaser → (mock)betalning → kvitto → upplåst rapport → ansökan → ärende, verifierad av 155 tester och webbläsartester; teamsamarbete, dokumentvalv, GDPR-export/radering, kuratorskonsol, inhämtningspipeline, deterministiska migreringar, seedad kunskapsbas.

What is mocked / incomplete

Swish-nätverksanropen (QR, callback, verifiering) — adaptern är en ärlig 503-stub; mock-betalning endast utanför produktion; webhooken avvisar allt; lösenordsåterställning/e-postverifiering saknas; anonymt köp utan konto finns inte; Storage-drivern ej integrationstestad mot riktigt Supabase-projekt.

Deployment blockers

Endast konfiguration + avtal: Supabase-/Vercel-projekt med hemligheter och domän; Storage-verifiering; Swish-avtal (och valet av Swish-variant); Resend-nyckel + SPF/DKIM; momsklassning bekräftad.

Vercel compatibility

GREEN — serverless-entry, cron-endpoints, storage-driver och rewrites finns och är röktestade; villkoren (poolad DB, supabase-driver, CRON_SECRET, migrering som deploysteg) är dokumenterade.

Supabase compatibility

GREEN — ren Postgres + förberedd RLS deny-all; Storage via driver; Auth/Edge Functions används medvetet inte (dokumenterade beslut).

AWS dependencies

Inga.

Swish status

Datamodell och kedja klara (payment-record med pending/confirmed/failed/cancelled; kvitto i samma transaktion; upplåsning härledd server-side). Nätverksintegrationen är inte påbörjad: ingen QR, ingen callback-verifiering. Blockerande beslut: Swish Företag vs Swish Handel vs betalpartner — det avgör om verifiering sker via mTLS-callback, polling eller PSP-webhook, och providergränssnittet är byggt för att ta emot vilket som helst.

Vendor map

Resend (mail) · SMTP (fallback) · Swish (stub) · Supabase Storage (driver) · ClamAV (valfri) · källwebbplatser (inhämtning med SSRF-guard). Ingen Stripe, ingen Kong, ingen AWS.

Secret / environment map

Se §10 — hemliga: DATABASE_URL, DIRECT_DATABASE_URL, AUTH_SECRET, FIELD_ENCRYPTION_KEY, SUPABASE_SERVICE_ROLE_KEY, CRON_SECRET, RESEND_API_KEY, SMTP_URL, SWISH_*. Samtliga enbart server-side; SPA:n har inga.

Security risks

HIGH: ingen lösenordsåterställning/e-postverifiering · MEDIUM: per-instans rate limiting; scan_unavailable-uppladdningar; kvarlämnade lagringsobjekt vid dokumentradering · LOW: oautentiserad /metrics (containervägen); Resend utan explicit timeout.

Estimated migration complexity

LOW — kodmigreringen är redan gjord och verifierad. Återstående arbete är plattformskonfiguration, förstadagsverifiering av Storage-drivern, och Swish-integrationen (den enda riktiga nya koden, ~en adapter + callback-verifiering när varianten är vald).

Recommended next architecture

Exakt den stack som redan är förberedd: GitHub → Vercel (SPA + en API-funktion + Cron) → Supabase (Postgres med RLS deny-all + privat Storage) · Swish engångsbetalning + QR → callback-verifiering server-side → befintligt payment-record som sanning → upplåsning · Resend för kvitton.
