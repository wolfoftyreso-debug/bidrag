3Supabase-beroenden

  • PostgreSQL — enda hårda beroendet. Ren SQL/Drizzle, inga extensions utöver standard (gen_random_uuid, sekvenser). Runtime ansluter via Supavisor-poolern (port 6543, transaction mode — kompatibelt: node-postgres använder inga namngivna prepared statements); migreringar går ALLTID mot direktanslutningen (5432) via DIRECT_DATABASE_URL.
  • Storage — dokumentvalvet med STORAGE_DRIVER=supabase: privat bucket, service-nyckel enbart server-side, REST-anrop med timeout. stoppunkt A — drivern är skriven mot Storage-API:et men aldrig körd mot ett riktigt projekt (kräver nycklar).
  • Auth/Edge Functions/PostgREST — används INTE. RLS deny-all + revoke gör PostgREST-ytan stängd (verifierat: 0 tabeller utan RLS; CI-invariant vaktar framtida tabeller).

4Migreringar & seed

7 deterministiska SQL-migreringar i apps/api/drizzle/: 0000 initial (schemat) · 0001 index · 0002 invites · 0003 payments · 0004 receipts + kvittosekvens · 0005 RLS deny-all + revoke · 0006 password_reset_tokens + provider_token. Körs med npm run db:migrate (Node 22, ingen extra tooling). Seed: npm run db:seed — idempotent, körs en gång vid uppsättning. Regel: migrera FÖRE koddeploy som behöver schemat; aldrig DDL via poolern.

5Lagring, auth, API-ytor

  • Lagring: uppladdningar (PDF/PNG/JPG/DOCX/XLSX/TXT, magic-byte-verifierade, opaka tenant-scopade namn) → Supabase Storage på Vercel. Ingen annan filsystemsanvändning i runtime.
  • Auth: egen (scrypt + JWT 15 min + roterande refresh, httpOnly-cookies, origin-guard, lösenordsåterställning). Kräver AUTH_SECRET ≥ 32 tecken; saknas den i produktion vägrar processen starta (fail-fast, verifierat i config).
  • API: ~62 REST-endpoints under /v1 i EN funktion — auth, profiler/projekt, matchning+teaser, betalning/kvitto (Swish + status/QR), ärenden, dokument, team/GDPR, kurator, cron. Webhook: POST /v1/webhooks/payments/swish (callback-URL:en kräver https:443 — Vercel uppfyller).

8DNS-krav

  • bidrag.se (apex) → Vercel: A-post 76.76.21.21 (eller ALIAS/ANAME enligt Vercels domänguide) · www → CNAME cname.vercel-dns.com. TLS utfärdas automatiskt av Vercel.
  • Resend-avsändardomän: SPF- och DKIM-TXT-poster (exakta värden ges i Resend-konsolen vid domänverifiering) + rekommenderad DMARC-post.
  • Swish-callback kräver ingen DNS utöver produktionsdomänen (https:443 uppfylls av Vercel).

9Production blockers & stoppunkter

Stoppunkt A — Supabase Storage-drivern: skriven mot Storage-REST men aldrig körd mot ett riktigt projekt (kräver nycklar). Verifieras i steg 3 nedan innan produktionstrafik.

Stoppunkt B — Vercels funktionsbygge av api/index.ts: funktionen importerar hela API:t över workspace-gränsen med explicita .ts-ändelser. Vår lokala serverless-simulering är grön, men Vercels egen bundler (nft/esbuild) kan inte köras härifrån och verifieras därför på FÖRSTA preview-deployen. Om den mot förmodan inte löser importerna är fallbacken liten och känd: peka funktionen mot förbyggd JS (apps/api/dist, byggs redan av npm run build) i stället för källfilerna.

  • Konton/hemligheter: Supabase-projekt, Vercel-projekt, domän, Resend-nyckel + domänverifiering (blockerar mail).
  • Swish: handelsavtal + certifikat → MSS-körning → en riktig 39 kr-betalning (scripts/swish-readiness.mjs). Blockerar betalvägen, inte lanseringen av gratisanalys/teaser.
  • Momsklassning bekräftad med redovisningen innan första riktiga kronan (VAT_RATE_BPS är konfigurerbar).

10Konkret plan: GitHub → Vercel + Supabase

  1. Supabase — skapa projekt (EU-region). Hämta poolad + direkt connection string. Skapa PRIVAT Storage-bucket documents. Kör från en utcheckning av main: 
    DIRECT_DATABASE_URL=<5432> DATABASE_URL=<5432> AUTH_SECRET=<prod> \
FIELD_ENCRYPTION_KEY=<prod> npm run db:migrate && npm run db:seed
  2. Vercel — importera GitHub-repot (root = repo-roten; vercel.json styr build/output/funktion/rewrites/cron). Sätt Node 22.x. Lägg in §7-variablerna med separata värden för Production/Preview. Verifiera stoppunkt B på första preview-deployen: /healthz → {"ok":true}.
  3. Storage-verifiering (stoppunkt A) — i preview: registrera testkonto, ladda upp PDF, ladda ner, GDPR-radera kontot; kontrollera i Supabase-konsolen att objekten skapas och försvinner.
  4. Preview-genomkörning — hela flödet: registrering → intag → teaser → (mock av i preview? nej: PAYMENTS_MOCK_ENABLED sätts ENDAST i preview, aldrig production) → kvitto → rapport; lösenordsåterställning med riktigt Resend-mail; cron: kontrollera i Vercel-loggarna att de fyra jobben kör grönt.
  5. Domän — koppla bidrag.se + www (DNS enligt §8), sätt PUBLIC_BASE_URL/CORS_ORIGIN till produktionsdomänen. Verifiera Resend-domänen (SPF/DKIM).
  6. Production-deploy — merge till produktionsgrenen → automatisk deploy. Rökkontroll: /healthz, registrering, teaser, dokumentvalv, återställningsmail till riktig inkorg.
  7. Swish-milstolpen (när avtal + cert finns) — MSS i preview (SWISH_API_BASE=https://mss.cpc.getswish.net, testcert) → node scripts/swish-readiness.mjs; därefter produktionscert + en riktig 39 kr-betalning med samma skript; återbetala i Swish-portalen. Först därefter är betalvägen live.
  8. Efterkontroller — Vercel-larm på funktionsfel; Supabase-backupper är på per default (verifiera PITR-nivå); kalenderpåminnelse för Swish-certets utgångsdatum.
