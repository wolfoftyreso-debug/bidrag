Migrering till Vercel + Supabase

Från containerantaganden till en avsiktligt tråkig beta-arkitektur: GitHub som källa till sanning, Vercel som bygg- och driftplattform, Supabase som hanterad Postgres och lagring. Ingen Kubernetes, ingen gateway, ingen Redis, ingen AWS.

2026-08-16 · Kodmigreringen klar och verifierad (107 API-tester gröna, serverless-röktest genom riktiga handlern) · Plattformskoppling återstår som konfiguration

1Nuvarande arkitektur

Monorepo med tre arbetsytor: packages/core (ren domänmotor, noll I/O), apps/api (Fastify 5 + Drizzle + PostgreSQL 16) och apps/web (Vite React SPA). Egen auth (scrypt, roterande refresh-tokens, httpOnly-cookies), pg-boss-jobb i en långlivad process, dokument på lokal disk, containerimage mot Kubernetes-manifest.

Den forensiska revisionen (20 punkter) fann fyra verkliga deployblockerare — och noll AWS-beroenden:

  • Migreringar och pg-boss-worker startades i processen (index.ts)
  • Dokumentvalvet skrev till lokal disk (UPLOAD_DIR)
  • Jobbschemaläggningen krävde den långlivade workern
  • Supabase-specifikt: public-schemat utan RLS är läsbart via PostgREST för alla med anon-nyckeln

Inga hemligheter i Git (skannat). Inga hårdkodade produktions-URL:er — SPA:n anropar bara /v1 på samma origin.

4Behållna komponenter — med skäl

  • Egen auth i stället för Supabase Auth. Dokumenterat starkt skäl: komplett, testad auth med tenants, roller, inbjudningar och roterande refresh är sammanvävd med behörighetsmodellen. Byte = stor omskrivning utan beta-värde. Kan omprövas senare.
  • Auktorisering i applikationslagret (tenant-scopad på varje query, verifierad av isolationstester). RLS är deny-all-muren mot PostgREST-vägen, inte applikationens behörighetsmodell.
  • Drizzle-migreringar versionerade i Git — samma garanti som Supabase CLI, noll omskrivning.
  • Vendor-anrop server-side i API:t. Edge Functions införs inte nu: att flytta fungerande server-side-kod till en andra runtime vore infrastruktur utan krav. Dokumenterat som framtida beslut om integrationsytan växer.
  • Dockerfile + deploy/k8s/ som alternativ egen-drift-väg — valideras i CI, driftas inte, ej primär.

5Borttagna beteenden

  • Migreringar vid processtart (kapplöpningsrisk i serverless) — nu deploysteg
  • Direkta filsystemanrop i rutter — nu bakom lagringsdrivern
  • Antagandet om en långlivad process för schemaläggning

6Vendor-integrationer

8Databasmigreringar

Deterministiska, committade, körs i CI och som deploysteg: 0000 initial · 0001 index · 0002 invites · 0003 payments · 0004 receipts · 0005 RLS deny-all.

Regel: ny tabell ⇒ ENABLE ROW LEVEL SECURITY i samma migrering. Invarianttestet listar varje tabell utan RLS och fäller CI — en ny tabell utan RLS vore ett öppet API mot dess data.

11Känd teknisk skuld

  • Rate limiting per funktionsinstans, inte globalt — acceptabelt för beta; global limitering är ett framtida beslut vid behov, inte en gateway.
  • Beta-observability = Vercels funktionsloggar + strukturerade pino-loggar + audit-tabellen; /metrics exponeras medvetet inte på Vercel. Larmkoppling är konfiguration, inte kod.
  • pg-boss-schemat ligger kvar i databasen (oanvänt på Vercel-vägen, ofarligt); städas om container-vägen pensioneras.
  • Kallstart bygger Fastify-appen (~hundratals ms första anropet per instans) — acceptabelt för beta.

12AWS

ingenting kräver AWS  Inga SDK-beroenden, inga tjänsteantaganden i kod. Ordets enda förekomster är kommentarer i de behållna Kubernetes-manifesten (alternativvägen) och gäller generisk egen drift.
